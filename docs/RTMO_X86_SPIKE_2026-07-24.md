# RTMO x86 spike

Date: 2026-07-24

Status: reproducible CPU adapter and synthetic comparison complete; real-player
and native-runtime qualification remain.

## Outcome

RTMO-s now has a strict VCG Motion adapter and an executable pinned x86
evaluation path. The adapter converts RTMO's COCO-17 pixel coordinates and
scores into the same portable `body.core17` shape used by the rest of the
Motion contract. Motion API `0.4.0` adds the honest closed source identity
`rtmo-native`; it does not change landmark, action, health, coordinate, or
bridge semantics.

The local RTMO-s ONNX model ran through `rtmlib` and ONNX Runtime's explicit
CPU provider on the owned Windows x86-64 development host. A paired MediaPipe
Pose Landmarker Lite process received the exact same deterministic 640 × 640
synthetic byte suite. This establishes executable compatibility and a narrow
negative/idle compute comparison. It does not establish tracking quality.

## Adapter boundary

[`rtmo-adapter.ts`](../packages/motion-contract/src/rtmo-adapter.ts) enforces:

- exactly 17 COCO-order keypoints and exactly 17 scores per backend candidate;
- finite pixel coordinates, scores in `[0, 1]`, positive image dimensions,
  bounded player count, and monotonic frame timing;
- normalization into `image.normalized.top-left` without clamping finite
  out-of-frame points;
- score as `visibility`, an explicit default observed threshold of `0.25`, and
  bounds derived only from observed landmarks;
- removal of RTMO's all-zero no-detection sentinel;
- deterministic confidence ranking when RTMO returns more candidates than the
  declared `maxPlayers`; and
- candidate-only, frame-local IDs. The adapter does not claim RTMO supplies
  persistent identity.

No action, world-coordinate, rich-landmark, or stable-ID capability is
fabricated. Downstream player-session tracking remains the identity authority.

## Reproducible model and environment

The isolated experiment is in [`experiments/rtmo`](../experiments/rtmo):

- Python is constrained to 3.13;
- all 27 resolved Python packages are frozen in `uv.lock`;
- `rtmlib` is pinned to `0.0.15`, ONNX Runtime to `1.27.0`, MediaPipe to
  `0.10.35`, and NumPy to `2.5.1`;
- the upstream RTMO-s ZIP is accepted only at 36,442,532 bytes and SHA-256
  `3da7ad88b209f9da8be87ba5c325610639af04de3b5c8a96649b98cd9e2848a2`;
- its sole accepted `end2end.onnx` payload is 39,617,685 bytes and SHA-256
  `d0703d40d19f3921da51ae725402d5fdae4d2478c7442072d3101bd396f370d8`;
  and
- model bytes stay under ignored `artifacts/rtmo/models`. They are not added to
  Git or treated as cleared redistribution material.

The preparation script bounds the download, verifies the archive before
parsing, accepts exactly one named model member, verifies expanded size and
digest, and publishes through a temporary file. The MediaPipe model uses the
existing project-pinned 5,777,746-byte asset with SHA-256
`59929e1d1ee95287735ddd833b19cf4ac46d29bc7afddbbf6753c459690d574a`.

PowerShell reproduction:

```powershell
$env:UV_PROJECT_ENVIRONMENT = (Join-Path (Get-Location) "artifacts/rtmo-venv")
uv sync --project experiments/rtmo --frozen
uv run --project experiments/rtmo experiments/rtmo/prepare_model.py

uv run --project experiments/rtmo experiments/rtmo/benchmark.py --backend mediapipe --output benchmarks/pose-backends/windows-x64-mediapipe-lite-cpu.json

```

## CPU comparison

Each backend ran sequentially in a separate process. Each received 20 warm-up
images and
100 measured images, cycling through exact black, gray-114, horizontal
gradient, and seeded-noise inputs. Every input is channel-identical so RTMO's
BGR convention and MediaPipe's sRGB convention receive equivalent pixels.
The reports name both interpretations and the backend-call-only timer plus
linear-interpolation summary method. The shared suite SHA-256 is
`21b8b49feb5e0b3cfb512c74d5bbda72bd3ffd0f39faecd3ce8f63d6470373d7`.
Neither report contains image bytes.

| Backend | Provider | p50 | p95 | p99 | Worst | Throughput | Peak process working set |
|---|---|---:|---:|---:|---:|---:|---:|
| MediaPipe Lite 0.10.35 | CPU | 9.571 ms | 10.090 ms | 10.431 ms | 10.505 ms | 104.182 FPS | 184,098,816 bytes |
| RTMO-s / rtmlib 0.0.15 | ONNX Runtime CPU | 56.334 ms | 60.987 ms | 62.568 ms | 64.183 ms | 17.923 FPS | 234,168,320 bytes |

On this narrow run, RTMO-s was 5.89× MediaPipe's p50, 6.04× its p95, and used
1.27× the peak whole-process working set. MediaPipe delivered 5.81× the
throughput. All four inputs produced zero detections in both backends, as
expected for a negative/idle compute fixture.

These values are observations, not a backend selection. RTMO is a one-stage
multi-person pose model, while this suite contains no people and exercises
none of the crowded-scene behavior that motivates it. The evidence cannot
rank landmark accuracy, occlusion recovery, player separation, ID switches,
action quality, or exposure-to-action latency.

## GPU boundary

The host's RTX 3080 Ti and installed driver expose a CUDA execution-provider
name through `onnxruntime-gpu`, but the provider could not load because the
required local CUDA 13/cuDNN runtime DLLs were absent. ONNX Runtime then fell
back to CPU. That attempt is deliberately excluded from the reports.

The tracked environment therefore pins CPU `onnxruntime`, and the benchmark
fails unless RTMO reports exactly `["CPUExecutionProvider"]`. Installing a
large system CUDA/cuDNN toolchain is not implicit experimental authority; see
Q-213.

## Sources and claim limits

- [MMPose RTMO project](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmo)
  describes the one-stage real-time multi-person model family and publishes
  the official ONNX artifact used here.
- [rtmlib](https://github.com/Tau-J/rtmlib) provides the Apache-2.0 Python
  inference wrapper and documents RTMO with ONNX Runtime.
- [rtmlib 0.0.15 on PyPI](https://pypi.org/project/rtmlib/0.0.15/) identifies
  the exact wrapper release frozen by the lockfile.
- [MediaPipe Pose Landmarker](https://ai.google.dev/edge/mediapipe/solutions/vision/pose_landmarker)
  remains the portable baseline path.

Upstream implementation and model availability do not establish VCG's right
to redistribute the model. The spike downloads ignored development evidence
from the official publisher and makes no shipping-license decision.

## Remaining qualification

I-051 remains active. Before selecting RTMO or integrating it into the native
host, the project still needs:

1. the same consented, minimized real-player recordings or synchronized
   skeleton/ground-truth session run through both pinned backends;
2. one-player and then two-player accuracy, missing-landmark, crossing,
   occlusion, identity-switch, action, and recovery results;
3. complete exposure-to-action latency and concurrent-workload evidence rather
   than inference-only timing;
4. native Linux x86-64 measurements and the actual Rust/ONNX Runtime process
   boundary;
5. a separately authorized and dependency-complete GPU run if GPU remains
   relevant; and
6. distribution-license review before any model is shipped.

Q-214 asks whether the paired real-player comparison may share the already
planned consented camera campaign. Until then, MediaPipe remains the
implemented browser baseline and RTMO remains a qualified-for-further-testing
candidate, not the selected production backend.
