# Console-managed game save lifecycle

Last updated: 2026-07-24

Status: software contract, path planner, and explicit durable reset primitive implemented; broader filesystem enforcement and target qualification remain

Authority: D-050, D-051, D-084, D-087, D-088, D-089, I-100, I-189, I-191

## Boundary

Console-managed saves are device-local game progress. They are not player
profiles, authentication, calibration, portraits, diagnostics, package files,
or hosted-service data. The console supplies no save backup, export, migration
to another console, or cloud synchronization. Healthy OS and game-package
updates preserve the writable data partition; storage loss, destructive
reflash, factory reset, or console replacement permanently destroys it.

The Rust `save_lifecycle` module is a pure, bounded planner for this boundary.
The separate host-only `save_reset` executor now persists and recovers one
explicitly confirmed exact-scope save/cache deletion. It does not yet create
ordinary runtime directories, mount sandboxes, move a save, persist profile
unlink/claim/migration, or enforce a filesystem quota. Those mutations remain
native-host and target-filesystem work.

## Namespace

Every local save and disposable cache path is derived only from host-owned
absolute roots and validated identifiers:

```text
<data-root>/games/<game-id>/<profiles|unassigned>/<opaque-owner>/<runtime>/saves
<cache-root>/games/<game-id>/<profiles|unassigned>/<opaque-owner>/<runtime>/cache
```

Game, profile, and slot IDs use the existing closed native intent grammar.
Unassigned owner and migration transaction IDs are exactly 32 lowercase
hexadecimal characters generated by the trusted host. Display names, browser
paths, package entrypoints, URLs, device IDs, and game-authored strings never
become path segments.

The namespace deliberately excludes package version. A healthy update or
rollback therefore resolves the same save root. A format change must use a
bounded sibling staging path and atomically replace the active save only after
validation; the planner exposes source, staging, and commit paths but does not
claim that crash-safe replacement is implemented.

Save and cache roots are separate. Cache may be deleted for space or release
changes; a save is never selected as cache cleanup.

## Runtime treatment

| Runtime | Console-managed local state | External boundary |
|---|---|---|
| Remote web | Dedicated per-game/per-owner browser profile storage | Reset affects only the local browser store. Hosted account/service data is explicitly unaffected. |
| Local web | Dedicated per-game/per-owner browser profile storage | No network or shared console origin is implied. |
| Native / Godot | Per-game/per-owner writable save mount | The game receives only its mount, never the root or profile vault. |
| Libretro | Per-game/per-owner save/state/remap directories | Content, cores, BIOS, configuration, saves, and cache remain distinct. |

The planner gives all four runtimes the same ownership, quota, reset, and
unlink vocabulary. Runtime adapters still have to prove that Chromium profiles,
native mounts, and RetroArch paths enforce it against hostile code.

## Quotas and low space

Save and cache quotas are separate host policy, not browser input. Zero or
greater-than-64-GiB save allocations and greater-than-64-GiB cache allocations
are rejected by the current safety ceiling; that ceiling is not a product
default or capacity recommendation. Every write reservation checks existing
usage, addition overflow, exact remaining bytes, and the applicable quota
before mutation.

Low-space policy may discard cache and refuse new writes with a visible error.
It must not silently truncate committed progress, borrow another game's quota,
or upload data. Final quota values, reserved recovery headroom, filesystem
accounting, and concurrent-writer enforcement remain I-022, I-100, I-162,
I-189, and I-191 work.

## Profile deletion and unassigned progress

Deleting a profile removes its portrait, calibration, body-matching data, and
save links. Each preserved console-managed slot is rewritten to a fresh opaque
unassigned owner. The persistent post-delete record contains no deleted profile
ID. Reusing a display name or creating another profile cannot claim it.

Unassigned progress can be played without ownership change. Claiming requires
an explicit target profile and refuses to produce a plan when that profile
already has the same game/slot; replacement, merge, keep-both, or delete must
be resolved deliberately by a later UX. A duplicate unassigned token, unsafe
token, wrong deleted owner, or already-profile-owned claim fails closed.

D-089 supersedes the Export action originally mentioned by D-088. Unassigned
progress can be viewed, played locally, claimed, or permanently deleted, but
the console provides no export path.

The pure native record transition is implemented and tested. A separate
bounded Svelte desk prototype now exercises sanitized synthetic entries,
Play Unassigned intent, explicit claim/conflict/delete flows, safe Back,
controller navigation, and camera-free shell-motion navigation without
claiming a native mutation. Durable unlink ordering, power-loss recovery,
trusted metadata sanitation, actual launch/deletion, and target household
qualification remain I-188 through I-191.

## Reset and no-egress rules

A reset plan names exactly one save root and its separate cache root. The
host-only executor requires preprovisioned disjoint roots, publishes a strict
path-free durable intent, removes only those exact canonical directories, and
recovers idempotently after either deletion. It never targets the game-data
root, another owner, package files, managed retro content, the profile vault,
or hosted-service state. Remote-web reset copy must state that a hosted service
may retain its own account data.

The contract contains no network destination, recovery archive, export file,
cloud account, profile-vault field, portrait, calibration value, or save
payload. All generated paths remain under host-owned roots. Tests cover remote
web, local web, native/Godot, and Libretro planning; path traversal; quota and
integer overflow; update namespace stability; bounded migration staging;
profile unlinking; token reuse; same-name recreation; claim conflicts; and
hosted-service reset disclosure.

## Remaining qualification

I-100's lifecycle design is complete, but production enforcement is not.
Required follow-up includes:

- signed per-release quota and save-format policy without changing manifest v1
  authority silently;
- browser profile isolation and OS/native mount confinement;
- durable atomic writes plus migration, unlink, claim, and unassigned delete
  under interruption; explicit exact-scope reset now has a durable primitive;
- actual filesystem quota and concurrent-writer accounting;
- low-space, full-disk, corruption, rollback, reinstall, and uninstall tests;
- sanitized game-authored metadata and hostile save formats;
- factory-reset and permanent-loss proof on both reference platforms; and
- inspection proving profile-vault data and save contents never enter each
  other, diagnostics, recovery images, or network traffic.
